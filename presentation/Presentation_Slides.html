📌 What We Are Doing

As part of the Storable Data Migration/Modernization Project, data is being migrated from PostgreSQL, Microsoft SQL Server, and AWS Athena into Snowflake. Migration Validator is the tool we're building to prove that migration was done correctly — for hundreds of tables, without hand-written SQL.

In Scope Right Now

  • Schema extraction across all 3 source dialects
  • Deterministic + AI-assisted column matching
  • Dialect-aware AI SQL generation (row count + full data)
  • Per-source exclusion policy (PostgreSQL / MSSQL / Athena)
  • Batch mode to validate hundreds of tables in parallel

Why It Matters

  • Every comparison is type-aware, not just row counts
  • Every run reports coverage — nothing skipped silently
  • One canonical plan (plan.json) is the audit trail
  • Rule book (base + learned) evolves without redeploys
  • Removes the manual-SQL bottleneck from the testing team

⚠️ Challenges We Solved

🧩

Four SQL Dialects, One Result

PostgreSQL, MSSQL, Athena/Trino and Snowflake each need different CAST/date/format syntax — one wrong function silently breaks a table's validation.

🕳️

NULL Never Equals NULL

SQL's own comparison rules mean two NULLs never match. Solved with a universal <<NULL>> sentinel wrapped around every normalized expression.

🔗

Ambiguous Column Names

created_at vs CreatedDate vs createdOn — exact matching alone isn't enough. Needed fuzzy scoring plus a narrow, token-efficient AI fallback.

🚫

AI-Only, No Silent Fallback

A degraded query that "looks right" is worse than no query. Required a 3-attempt self-correction loop instead of ever guessing.

📏

Scaling to Hundreds of Tables

One-by-one runs don't scale. Built a parallel batch orchestrator driven by a single tables.yaml, with a manifest reporting per-table pass/fail.

🔐

Exclusions Differ Per Source

MSSQL rowversion columns aren't a PostgreSQL or Athena problem. Split exclusion policy into one file per source type, applied to both source and Snowflake target.
